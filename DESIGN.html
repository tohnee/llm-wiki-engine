01总览与核心理念

核心洞察(Karpathy llm-wiki):停止反复推导,开始编译。RAG 检索后即忘;wiki 累积并复利。本系统在此基础上吸收 llm-wiki v2 与 obsidian-wiki 的生产经验,把它做成企业级、多租户、有生命周期的知识引擎。

两层不变量(贯穿全系统)
  • 导航层可有损,证据层必须无损。 Fact / Entity / Relation / Wiki 都是"答案在哪"的指针;原文 span 是唯一 citation 落点,回答"答案是什么"。KG 指挥检索,而非取代检索
  • tenant_id 由网关从 JWT 解出、服务端强制注入。 agent、文档内容、请求体里任何 tenant 字段一律忽略。

系统拓扑

对外服务用 JWT;调 evidence 用 HMAC 内部签名。模型调用全程 Messages API,多租户隔离发生在 LLM 之外的存储与鉴权层。

02Wiki 引擎:编译管线

引擎把"PDF → 答案"拆成可并行、可增量、可分级的编译 DAG。每个单元 hash = sha256(content + prompt_version + model_id),增量编译与 prompt 升级共用一套失效机制。

编译 DAG(L0–L4)

并行 + Streams

每层 worker 无状态全并行,层间靠 Redis hash 计数器协调。run_worker 消费 compile:L1。

增量 manifest

记录源→派生产物(fact/entity/wiki),改动只重算受影响单元及其下游。

分级深度

D0 分钟级可问 · D1 +事实/实体 · D2 +关系/Wiki

成本工程

Pass模型通道说明
L1/L2 抽取HaikuBatch API量最大,成本减半、不占交互配额(≥30 chunk 触发)
L3 关系 / L4 WikiSonnet实时低优先级量小、增量
prompt caching——同 chunk 多 pass 共享原文前缀,命中率目标 ≥70%

三层架构(对齐 v2)

raw(原文 span,不可变)/ wiki(AI 生成,仅视图)/ schema(规则层,每租户可配 taxonomy、关系类型、lint 阈值、自定义规则)。schema 是"最重要的文件"——把通用 LLM 变成有纪律的知识工作者。

03记忆生命周期(v2 的"缺失层")

把扁平的等权事实升级为有生命周期的活模型。这是相对 Karpathy 原版与 obsidian-wiki 的关键扩展。

置信度 confidence

由来源数 + 最近确认 + 是否被矛盾共同决定。1源≈0.5,3源≈0.75;矛盾 ×0.5,过时 ×0.3。

遗忘 forgetting

Ebbinghaus 指数衰减 retention = e^(−Δt/τ)。架构类 τ=365 天(慢),瞬时状态类 τ=30 天(快)。

强化 reinforcement

同一 (主语,谓词,宾语) 再次被抽到 → source_count++、刷新确认时间、retention 重置为 1。

取代 supersession

矛盾解决:按 来源数/最近确认/retention 提议胜者,败者标 stale + superseded_by(版本化保留,不删)。

巩固分层 consolidation tiers

每升一层:更压缩、更高置信、更长寿。crystallize 把问答线程蒸馏成 wiki 页 + 回填事实(质量门控,on_query 异步触发)。

事件钩子(自动化"记账")

on_source · on_session_start · on_session_end · on_query · on_memory_write · on_schedule —— 把维护负担降到接近零,人只管思考。

04检索与取证

navigation-first + span-grounded:KG 先缩小范围,检索保证细节,agent 多轮取证,verify 拦截幻觉。

分层检索(成本随规模平坦)

层动作停止条件
tier-0只读 ≤200 字摘要扫描(index-only 可强制)摘要可答即停,标注"未读正文"
tier-1BM25+向量 → RRF → cross-encoder rerank,按 tier 加权span 级证据
tier-2span → parent chunk 上下文扩展补充上下文

KG 多跳导航

navigate 用 embedding 实体链接 → 沿 relations BFS 扩 1–2 跳 → 聚合邻域文档为 scope,并返回关系边。/neighbors 给子图,/graph/export 出 json/graphml/cypher/html。"项目为什么超预算"经 项目→预算/实际成本/变更 把关联文档全拉进来。

取证循环 + 校验

Router(Haiku 分流 simple/complex)→ Fast/Agentic tool loop(navigate/search/read_span/expand/lookup_entity/neighbors)→ verify 逐 claim NLI 校验 → 不足自动升级多跳。每条结论回链 [doc:span]。

07数据模型

证据层(无损)

Span 100–300 token,citation 落点,带版面 bbox 回链。Chunk 800–1500 token 上下文单元,带 summary/tier。

导航层(可有损)

Fact(SPO + qualifiers + provenance + 生命周期字段)· Entity(canonical + 跨文档 mention)· Relation(typed)· WikiNode(仅视图)。

生命周期/治理表

facts 含 source_count / created_at / last_confirmed / retention / superseded_by / stale;conversations(会话记忆)· observations(巩固分层)· audit_log(审计)· tenants/users(注册表)。核心 7 表按 tenant LIST 物理分区。

08多租户隔离与治理

维度机制
租户隔离① 7 表按 tenant LIST 物理分区 ② 服务端强制注入 tenant ③ 跨租户探测拦截(read_span 校验归属 + HMAC 防伪)
用户隔离会话与记忆按 tenant:user:session 三元组分键;同租户内共享知识库(企业模型:知识共享、对话隔离)
会话隔离Redis 热副本 + Postgres 持久副本,worker 无状态按键恢复
鉴权JWT(pbkdf2 密码)对外;HMAC 签名 header 服务间;角色 admin/member/viewer
隐私入库前 PII/密钥脱敏(API key/Bearer/邮箱/手机/身份证/私钥块)
审计每个写操作留痕 audit_log(ingest/crystallize/supersede/daily…)
执行隔离问答 agent 只读工具面免 sandbox;编译/执行 agent 上 gVisor pod + 出口白名单
多租户用 API 还是 Agent SDK?

多租户隔离与用哪个 SDK 无关——它是存储分区 + 鉴权 + 服务端 ACL 的架构问题,在 LLM 调用之外完成。模型调用全程 @anthropic-ai/sdk / anthropic(Messages API),不是 Agent SDK。只有未来"agent 自主跑代码生成文件"才考虑 Agent SDK,且放进隔离 worker。

09部署

本地:docker compose up 起 9 服务(pg/redis/minio/evidence/query/admin/ingest/compile-worker/generation),前端 npm run dev。生产:K8s,compile-worker 走 gVisor + KEDA 按流深扩缩,query 用 HPA;密钥入 Secret;PG/Redis 建议托管。

测试:离线冒烟 41 项(make smoke,CI 必跑)+ 前端 esbuild 编译校验 + 端到端集成矩阵(鉴权/跨租户/viewer 限权/渐进可问/多跳/PII/结晶/衰减)。详见《部署与测试工程文档》。
